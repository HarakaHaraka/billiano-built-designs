# Billiano Built Designs

**Sustainable Building Services & Energy Design**

This repository is the **single source of truth** for the Billiano Built Designs
website and admin system. Everything flows one way:

> **edit → commit → push to `main` → automatic deploy.**

No more drag-and-drop deploys. If it isn't in this repo, it isn't on the site.

- **Public site (frontend):** static single-page app, deployed on **Netlify** →
  <https://billianobuiltdesigns.co.uk>
- **Admin system (backend):** password-protected Express + SQLite app, deployed on
  **Render**, completely separate from the public site.

## The golden rule — how changes go live

Every change to the website is made by editing a file in this repository and saving it
back to the `main` branch. The moment that happens, Netlify rebuilds and publishes the
site automatically — usually within a minute or two. There is **nothing else to do**: no
uploading, no drag-and-drop, no "publish" button.

If you use GitHub in the browser:

1. Open the file you want to change on <https://github.com/HarakaHaraka/billiano-built-designs>.
2. Click the **pencil (Edit)** icon.
3. Make your change.
4. Scroll down, write a short note of what you changed, and click **Commit changes**
   (commit straight to `main`).
5. Wait ~1–2 minutes — the live site updates itself.

## Owner how-to (no coding required)

### Add a portfolio project

The Portfolio page is built from a simple data file — **you never touch the page layout**.
Edit **`frontend/public/data/projects.json`**. Each project is one block like this:

```json
{
  "id": "riverside-heat-pump",
  "title": "Riverside cottage — air-source heat pump",
  "workType": "Heat pump design",
  "outcome": "Designed a low-temperature ASHP system; installed and commissioned.",
  "photo": "/data/photos/riverside.jpg"
}
```

- **`id`** — any short unique label (lowercase, dashes).
- **`title`** — the project name shown on the card.
- **`workType`** — a short tag (e.g. "Retrofit", "Heat pump design").
- **`outcome`** — one or two sentences on what was delivered and the result.
- **`photo`** — path to an image. Put the image in `frontend/public/data/photos/` and
  reference it as `/data/photos/yourfile.jpg`. Leave as `""` if you have no photo yet.
- **Important:** do **not** include `"placeholder": true` on a real project — that flag is
  only on the three sample cards and it shows the "Placeholder" tag. Delete the three
  sample entries once you have real work to show.

Commit the file. The new card appears automatically.

### Update an accreditation from placeholder to real

The accreditation register lives in **`frontend/public/assets/app.js`**, in the
`accreditations` section. Search the file for the word **`PLACEHOLDER`** or the exact text
you want to replace, and change it. For example, to add a real "Planned" accreditation,
find this line:

```js
${registerRow('<span class="status-pill status-planned">Planned</span>', ph('planned accreditation(s) — confirm names before listing'), '')}
```

and replace the `ph('…')` call with the real name in quotes, e.g.:

```js
${registerRow('<span class="status-pill status-planned">Planned</span>', 'MCS certification', 'Application submitted')}
```

To **move a credential between the four statuses** (Held / In progress / Planned /
Partner-held), copy its `registerRow(...)` line into the relevant card and change the
`status-pill` class to match (`status-held`, `status-progress`, `status-planned`, or
`status-partner`). When ICO registration is confirmed, change its pill from
`status-progress` "In progress" to `status-held` "Held" in the three places it appears
(search for `ICO registration`).

### Fill in the company number & insurance details

- **Company number** appears in two places — the site footer
  (`frontend/public/index.html`, search `company number`) and the accreditations page
  (`frontend/public/assets/app.js`, search `company number`). Replace the
  `PLACEHOLDER: company number` with the real Companies House number.
- **Insurance table**: in `frontend/public/assets/app.js`, the three insurance rows use
  `tc()` (which renders "to confirm"). Replace each `tc()` in the `insuranceRow(...)`
  definition with the real insurer name, policy number and level of cover in quotes. Do
  this only when you have the real policies in hand.

> Every placeholder currently on the site is listed with its exact location in the
> [FINAL CHECKLIST](#final-checklist--every-placeholder-to-replace) at the bottom.

## Frontend — run & build locally

Requires Node 18+.

```bash
cd frontend
npm install
npm run build      # compiles Tailwind into public/assets/app.css
# then open public/index.html via any static server, e.g.:
npx serve public   # or: python3 -m http.server -d public 8080
```

- `npm run build` — one-off production CSS build (what Netlify runs).
- `npm run watch` — rebuild the CSS automatically while you edit.

The site is a single-page app: navigation happens instantly with no full-page reload.
Deep links (e.g. `/accreditations`) work because Netlify serves `index.html` for any
unknown path (configured in `netlify.toml`).

## Admin backend — run locally & deploy

The admin system is a separate Express app in `backend/`. It is **password-protected**,
stores data in **SQLite**, and has two kinds of user:

- **Owner** — full access: projects, financials (cost, quote, commission, margin),
  professionals, expenditures, receipts, and user management.
- **Limited** — a professional who can log in and add **only their own** inventory costs,
  labour and receipts on the projects they are **assigned to**. They can never see other
  professionals' figures, company margins, or commission. These rules are enforced on the
  server, not just hidden in the screen.

### Run it locally

```bash
cd backend
npm install
cp .env.example .env          # then edit .env — set a SESSION_SECRET and OWNER_* values
npm run seed                  # creates the first owner account from OWNER_* in .env
npm start                     # http://localhost:4000  → /login
```

`npm run seed` is safe to re-run; it updates the owner's password rather than creating
duplicates. Health check: `GET /health` returns `{"status":"ok"}`.

### Environment variables

All variables are documented in **`backend/.env.example`**. Summary:

| Variable          | What it is                                            |
| ----------------- | ----------------------------------------------------- |
| `PORT`            | Port to listen on (Render sets this automatically).   |
| `NODE_ENV`        | `production` on Render (enables secure cookies + CSP). |
| `SESSION_SECRET`  | Long random string that signs the login cookie.       |
| `DATABASE_PATH`   | Where the SQLite file lives (on Render: the disk).    |
| `UPLOAD_DIR`      | Where receipt uploads are stored (on Render: the disk). |
| `OWNER_USERNAME`  | First owner login (used once by `npm run seed`).      |
| `OWNER_EMAIL`     | First owner email (optional).                         |
| `OWNER_PASSWORD`  | First owner password (used once by `npm run seed`).   |

**Never commit a real `.env`.** Only `.env.example` is tracked.

## Deploy pipeline

### Netlify (frontend)

`netlify.toml` (in the repo root) pins the build:

- **Base directory:** `frontend`
- **Build command:** `npm run build`
- **Publish directory:** `frontend/public`
- **Production branch:** `main`

To confirm the live domain builds **from this repo** (not the old drag-and-drop project):

1. Log in to **Netlify** → **Sites**.
2. If a site connected to this GitHub repo does not yet exist:
   **Add new site → Import an existing project → Deploy with GitHub →** choose
   **`HarakaHaraka/billiano-built-designs` →** set the production branch to **`main`** →
   **Deploy**. Netlify reads `netlify.toml` automatically.
3. On that site's **Deploys** tab you should see builds triggered by commits to `main`.

### Moving the domain off the old drag-and-drop site

The custom domain `billianobuiltdesigns.co.uk` may still be attached to the **old**
drag-and-drop Netlify site. Move it to the new repo-connected site like this (exact
click-path):

1. **Remove it from the old site:** Netlify → open the **old** site →
   **Site configuration → Domain management → Custom domains →** click
   `billianobuiltdesigns.co.uk` → **Options (⋯) → Remove domain**.
2. **Add it to the new site:** Netlify → open the **new** (repo-connected) site →
   **Domain management → Add a domain →** type `billianobuiltdesigns.co.uk` → **Verify → Add**.
   Add the `www` variant too if you use it.
3. Netlify re-provisions the free HTTPS certificate automatically (**Domain management →
   HTTPS → Verify DNS / Provision certificate** if it doesn't start on its own). Because
   the DNS already points at Netlify, there is usually no DNS change to make.
4. Once the new site serves the domain, you can **delete the old drag-and-drop site** so it
   can never be published to again.

> After this, the red banner error from the old build
> (`Uncaught SyntaxError … /_ds/organic-*`) is gone for good — this repo contains no such
> reference.

### Render (backend)

`render.yaml` (repo root) is a Render **Blueprint** for the admin service:

1. Render → **New → Blueprint** → connect **`HarakaHaraka/billiano-built-designs`**.
2. Render reads `render.yaml`: it creates a Node web service with root directory
   `backend`, a **1 GB persistent disk** mounted at `/var/data` (so the SQLite database and
   uploaded receipts survive every redeploy), and pre-fills most environment variables.
   > A persistent disk requires a **paid Render plan** (`starter` is set in the blueprint);
   > the free tier has no persistent disk and would wipe data on each deploy.
3. Set the three secret variables when prompted (they are marked "sync: false"):
   **`OWNER_USERNAME`**, **`OWNER_EMAIL`**, **`OWNER_PASSWORD`**. `SESSION_SECRET` is
   generated for you.
4. After the first deploy, open the service's **Shell** and run **`npm run seed`** once to
   create the owner login. Then visit the service URL → `/login`.
5. `autoDeploy` is on, so future pushes to `main` redeploy the backend too.

## The honesty rule

This site follows a strict honesty rule that **overrides every design and content choice**:

> No accreditation, insurance, membership, project, testimonial, statistic or client is
> shown as real unless it is confirmed. Everything else is a clearly marked
> **⚑ PLACEHOLDER** (or "to confirm"). A single false accreditation claim can permanently
> disqualify the company from public tenders — **when in doubt, leave it as a placeholder.**

Confirmed facts already on the site: the company is an incorporated Ltd; the owner holds a
**BEng (Hons) Mechanical Engineering** and a **PG Cert Sustainable Engineering**; **ICO
registration is in progress**; insurances are being purchased (shown as "to confirm"). The
four-status accreditation register is intentionally transparent — partners respond well to
honest gaps.
